# Project

My habit when building: first work out whose problem it solves, then decide on the technology. Each project below tries to state *why it exists* and *what it achieved*, not just a list of buzzwords.

## How I pick projects

- **A real user** — even if that user is only me, the scenario has to be concrete
- **Finishable alone** — walking the whole path from design to launch teaches the most
- **Leaves something behind** — either reusable code or a written retrospective

## On choosing technology

I prefer to **build the plain version first**. A few hundred lines of vanilla code is often easier to maintain and to understand than pulling in a whole framework. Bring in the framework once the requirements genuinely get complex — by then you know exactly what it is buying you.

```js
// Simple first: if it can be written clearly, don't write it cleverly
const render = (items) => items.map(toCard).join('');
```
