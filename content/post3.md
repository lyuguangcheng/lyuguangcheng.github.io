# 页面打开太慢，我先查了这五件事

一说到性能优化，很多人第一反应是「上打包工具、上 CDN、上懒加载」。但真正拖慢页面的，往往是几个非常朴素的原因。我的排查顺序是这样的：

## 1. 首屏到底加载了什么

打开开发者工具的 Network 面板，按体积排序。如果前三个文件占了 80% 的体积，那答案基本就在那里了。

- 图片有没有压缩、有没有按显示尺寸出图
- 字体是不是一次加载了五种字重
- 有没有引用根本没用到的大体积库

## 2. 有没有阻塞渲染的资源

CSS 和同步 `<script>` 都会挡住首屏。同步脚本能挪到 `</body>` 前就挪，非关键的加上 `defer` 或 `async`。

```js
// 只做一件事的脚本，没必要让整个页面等它
document.addEventListener('DOMContentLoaded', init);
```

## 3. 图片是不是懒加载了

首屏之外的图片，全部加上 `loading="lazy"`。一行属性，往往省下几兆流量：

```html
<img src="cover.svg" alt="封面" loading="lazy" width="1200" height="675" />
```

> 顺手写上 `width` 和 `height`，还能避免图片加载完成时页面「跳一下」。

## 4. 有没有重复请求

同一份数据被三个组件各拉一次，是最常见的浪费。加一层缓存，或者把请求提到上层统一处理。

## 5. 最后才看构建产物

到这一步才是打包工具的事：拆包、压缩、Tree Shaking。

## 我的经验

| 问题类型 | 出现频率 | 修复成本 |
| --- | --- | --- |
| 未压缩的大图 | 很高 | 极低 |
| 阻塞渲染的资源 | 高 | 低 |
| 重复请求 | 中 | 中 |
| 构建配置 | 低 | 高 |

**先量，再改，改完再量。** 凭感觉优化，通常只是把复杂度和体积一起加上去了。
